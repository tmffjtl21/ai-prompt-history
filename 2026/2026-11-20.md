  **A.** 세트 묶기 로직 약 70줄과 관련 DTO 필드, 조인을 뺐다. 공용 훅의 세트 분기는 구 API가 쓰고 있어 남겼다. 컴파일과 `pnpm tsc`는 통과했다.

- **[16:23] Q.** batch로 et_client_base_20261120 테이블에 거래처 데이터 넣으려면 어떻게 해야돼?

  **A.** local 프로파일로 띄우면서 통합회원 주소만 실행 옵션으로 덮어쓰면 된다. jar가 9월 빌드라 다시 빌드해야 한다. dev-member 전체 건수는 112,068건으로 현재 `et_client_base`와 같다.

- **[17:14] Q.** 시트 기준으로 일반인/의료인/의료기관 구분은 어떻게 되어야 하지?
  **A.** 세 구분은 거래처 코드가 아니라 통합회원이 내려주는 회원 정보(롤)로 정한다. 그래서 거래처 코드가 바뀌어도 그대로 동작한다. 거래처 코드로 나눠야 하면 마지막 칸(Lv2)을 본다. `201`~`210` 의료기관, `219` 의료인, `220` 일반인이다. `229`(약 12,200건)는 코드로 알 수 없다.

- **[17:30] Q.** 그럼 비어있는 회원은 어떻게 해?
  **A.** 분류 코드가 빈 거래처는 340건, 연결 회원은 164명이다. 세 구분과 개인·사업자 구분은 영향이 없다. 통합회원에 채워 달라고 요청하는 것이 맞다. 그때까지는 계정그룹(첫 칸)으로 처리한다.

## 이슈와 배운 점
- **`_ML` 테이블 언어 조건 누락**: ko 행만 있을 때는 드러나지 않았다. en·ja 행이 들어오면 `selectOne` 오류나 행 중복이 난다. 다국어 테이블 조인에는 항상 `LANG_CD` 조건을 넣는다.
- **프론트 `restApi`는 예외를 던지지 않는다**: 실패하면 `payload`가 null이다. 화면의 TypeError는 API 실패를 먼저 의심한다.
- **`BETWEEN ... AND CURDATE()`**: `CURDATE()`는 오늘 0시라 오늘 데이터가 빠진다.
- **`spring.config.import`로 가져온 설정이 우선한다**: 라이브러리 yml에 값을 두면 쓰는 앱 설정으로 덮어쓸 수 없다.
- **로그는 logback 로거 레벨로 끈다**: `log.info`로 찍는 로그는 쓰는 쪽에서 WARN으로 두면 된다. 라이브러리에 프로퍼티를 만들 필요가 없었다.
- **logback 로거 이름**: `com.zaxxer.hikari.HikariPool`은 틀린 이름이다. 실제는 `com.zaxxer.hikari.pool.HikariPool`이다.
- **요약 테이블은 배치 산출물**: `pr_goods_base_ml`에 넣기만 해서는 목록·주문내역에 반영되지 않는다.
- **`ko.json`에만 있는 키**: en·ja에서는 코드의 한글 `defaultMessage`가 그대로 나온다.
- **주문 조회 쿼리**: 회원·기간 조건 없이 돌리면 전체 정렬로 2분 넘게 걸린다.
- **PK 없는 복사 테이블**: `ON DUPLICATE KEY UPDATE`가 동작하지 않아 재실행 시 중복이 쌓인다.
- **토큰 노출**: 토큰 비교 중 마스킹 실수로 값이 명령 출력에 찍혔다. 외부 전송은 dev-member 호출 한 번뿐이다. 출력 전 마스킹을 확인한다.
- **단순화 시 동작 변경**: 새 주문목록 첫 버전은 송장 분리·수량 보정을 임의로 뺐다가 되돌렸다. 기존 동작을 바꿀 때는 먼저 확인한다.
