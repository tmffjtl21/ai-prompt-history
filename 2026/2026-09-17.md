## 질문과 답변 기록

- **[09:37] Q.** api 통합으로 트랜잭션이 묶였다는데, 주문취소 시 마일리지 복구가 잘 되는지 어떻게 확인하나?
  **A.** shell의 `MileageLocalCallAspect`가 REST 호출을 가로채 같은 프로세스에서 `saveMlgUseRfd`를 직접 부르고, 트랜잭션 경계는 `ClaimService.doClaim`이다. 검증은 기동 로그의 어스펙트 적용 문구 → 취소 후 DB 조회 → 트랜잭션 trace 로그의 "Participating in existing transaction" → 마일리지 다음 단계를 강제 실패시켜 롤백 확인 → `local-call.enabled=false` 대조군 순서로 한다. 검증 테스트는 어디에도 없다.

- **[09:47] Q.** feature.mileage.nonBlocking 이건 어디 소스에 있어?
  **A.** order 모듈 `MileageStrategy.java` 한 곳뿐이다. `cancel` 메서드에서 환불 응답 null 또는 예외 시 true면 warn 로그만 남기고 취소를 계속 진행한다. 어느 yml에도 키가 없어 기본 false이며, 모놀리식 전환과 무관한 AS-IS 코드다.

- **[09:49] Q.** nonBlocking 이거 무슨 뜻이지?
  **A.** 여기서는 마일리지 실패가 취소를 막지 않는다는 뜻이다. 예전에 member가 별도 서버라 네트워크 장애 완충용이었을 것이다. 지금은 같은 트랜잭션이라 실패는 정합성 문제이므로 켜면 안 된다.

- **[09:53] Q.** nonblocking의 원래 의미도 설명해줄래?
  **A.** 원래는 호출한 쪽이 작업 완료를 기다리며 멈추지 않는다는 I/O·동시성 개념이다. 이 코드의 플래그는 "실패해도 업무를 막지 않음"이라는 빌려 쓴 이름이라 fail-open에 가깝다. 원래 의미를 아는 사람이 보면 오해하기 쉬운 작명이다.

- **[09:54] Q.** 비동기랑 논블록킹은 다른 거지? 이해할 수 있게 설명해줄래?
  **A.** 다른 축이다. Blocking/Non-blocking은 제어권이 바로 돌아오느냐, Sync/Async는 결과를 누가 알려주느냐다. 네 가지 조합이 모두 존재하며, 식당 진동벨 비유로 정리했다.

- **[09:59] Q.** 블록킹과 논블록킹을 모르겠어. 코드로 자세히 설명해줄래?
  **A.** 그 줄에서 스레드가 기다리면 blocking, 일이 안 끝났어도 즉시 돌아오면 non-blocking이다. `read()` vs `configureBlocking(false)`, `take()` vs `poll()`, `Future.get()` vs `CompletableFuture.thenAccept` 예시로 설명했다.

- **[10:11] Q.** 콜백 API로 받는 방식이면 그건 이미 비동기+논블록킹이었네?
  **A.** 맞다. 업무 흐름 층위에서는 비동기 + non-blocking이다. 다만 개별 HTTP 호출은 접수 응답까지 스레드가 대기하므로 동기 + blocking이다. 토스 결제 웹훅이 이 형태다.

- **[10:14] Q.** DB가 JDBC를 쓰니 동기+블록킹으로 구현해야 하는 거 아냐? WebClient도 결국 block()으로 처리하는데.
  **A.** 맞는 진단이다. JDBC는 스펙 자체가 동기이고 트랜잭션도 ThreadLocal 커넥션 전제라 `.block()`이 맞는 선택이다. 완전 non-blocking은 WebFlux + R2DBC로 스택을 통째로 바꿔야 해서 업무 API에는 손해다. 단 리액티브 스레드 안에서 `.block()`을 부르면 예외가 나니 주의.

- **[10:17] Q.** 그럼 aurora-x2bee-gw는 논블록킹으로 되어 있어?
  **A.** Spring Cloud Gateway 위라 골격은 non-blocking이고 `.block()`, JDBC가 없다. 다만 `X2GlobalFilter`에서 요청 본문을 `subscribe` 후 즉시 읽어 값이 안 잡히고, 응답마다 스레드 풀 10개를 새로 만들어 shutdown하지 않는다. Kafka가 꺼져 있어 현재 운영 영향은 없다.

- **[13:20] Q.** 회원탈퇴 여부 체크에서 "잔여 마일리지가 있습니다"가 계속 나오는데 확인 쿼리 좀 알려줄래?
  **A.** `chkWithdrawalMember`가 mbrNo와 대표 cimsClientNo 두 키로 `getMilgSum`을 호출해 하나라도 잔액이 있으면 탈퇴 불가다. 그런데 이 테이블의 MBR_NO는 실제로 거래처번호 기준이라, cimsClientNo가 34603인 다른 거래처의 마일리지가 잡히면 오탐이 난다. dev DB 접속이 거부돼 stage로만 확인했고 두 키 모두 행이 없었다.

- **[15:07] Q.** 운영 코드가 dev-gerp 브랜치에서 어떻게 바뀌는지 다른 프로젝트들도 비교해서 알려줄래?
  **A.** MBR_NO → CIMS_CLIENT_NO 전환이 api-member, api-bo는 완료, batch-mbod, batch-gddp는 미전환이다. 탈퇴 체크 키 수집 블록은 두 브랜치가 동일해 오탐 문제가 그대로 남는다. dev 스키마에는 MBR_NO 컬럼이 없어 운영 코드를 dev DB에 붙이면 오류가 난다.

- **[15:19] Q.** batch 쪽에서 mbrNo 참조하는 곳 좀 더 자세히 확인해줄래?
  **A.** batch-mbod는 소멸 배치(`MileageRemoveConfig`) reader/writer 3개, 소멸 알림톡 UNION 쿼리, 가상계좌 미입금 취소 `updateMeMbrAstSum`이 MBR_NO를 쓴다. 가상계좌 취소 SQL은 MySQL에서 문법 오류이고 주체도 어긋나 운영에서도 정상 동작이 어려워 보인다. batch-gddp는 지급 배치 `BatMilgPayMapper`가 MBR_NO, IND_MBR_YN을 조회해 dev에서 실패한다.

- **[15:42] Q.** 이거 md 파일로 만들어줄래?
  **A.** api-member 하위 `docs/mileage-cims-batch-migration.md`로 작성했다. 배경, 스키마 현황, 프로젝트별 전환 현황, batch 상세, 수정 대상 파일, 탈퇴 체크 부록으로 구성했다. `docs` 디렉터리 커밋 여부는 확인 필요.

- **[16:16] Q.** 바탕화면 적립금.png 메뉴 기준으로 어디가 바뀌어야 하고 어디가 빠졌는지 분석해줄래?
  **A.** 문서 7장에 메뉴별 판정을 추가했다. 적립금 만료 조회·거래처별 조회는 api-bo SQL 미전환, 회원상세 거래처별 자산은 최근 사용일 서브쿼리 MBR_NO 잔존, BO 프론트 일괄변경·엑셀 업로드는 아직 mbrNo를 보낸다. 회원상세 자산/혜택 탭은 회원번호를 거래처번호 자리에 넘겨 항상 0이 나오므로 정책 결정이 필요하다.

## 이슈와 배운 점
- **트랜잭션 묶음 미검증**: 주문취소와 마일리지 환불이 같은 트랜잭션에 있다는 근거는 코드 구조뿐이고 테스트가 없다. 원자성 증명은 실패 케이스여야 하며, 어스펙트 off 대조군까지 있어야 한다.
- **`feature.mileage.nonBlocking`은 조용한 유실 경로**: 켜면 취소는 커밋되고 마일리지는 복구되지 않는다. 검증 시 반드시 false 상태로 확인한다.
- **SAP 취소전표 비대칭**: 취소 경로 FI0013은 보상 등록이 없어 DB 롤백 후에도 SAP 전표가 남을 수 있다.
- **non-blocking 작명 주의**: 스레드 대기 여부와 무관한 "fail-open" 의미로 non-blocking을 쓰면 오해를 부른다.
- **`.block()`은 서블릿 스레드에서만 안전**: 리액티브 스레드 안에서 부르면 `IllegalStateException`이 난다. 스케줄러나 WebClient 콜백 안에서 RestApi 재호출 시 주의.
- **게이트웨이 활동 로그 필터**: `subscribe` 후 즉시 값을 읽는 코드와 요청마다 스레드 풀을 만드는 코드가 있다. Kafka를 켜면 스레드가 쌓인다.
- **탈퇴 체크 오탐 원인**: 회원번호를 거래처번호 컬럼에 그대로 조회한다. 회원번호와 같은 값의 거래처번호가 있으면 다른 거래처 마일리지가 잡힌다.
- **마일리지 키 전환 누락**: batch-mbod, batch-gddp, api-bo 일부 SQL, BO 프론트가 MBR_NO/mbrNo를 그대로 써서 dev/gerp 스키마에서 "Unknown column"으로 실패한다.
- **가상계좌 미입금 취소 SQL**: `UPDATE ... SET ... FROM` 구문은 MySQL 문법 오류이고 파라미터도 객체를 넘긴다. 운영 동작 여부 확인 필요.
