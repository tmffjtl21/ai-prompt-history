## 질문과 답변 기록

- **[11:18] Q.** `ObjectOptimisticLockingFailureException` (RecentGoods#12399) 이 오류 어떻게 하면 나는 거지?
  **A.** `RecentGoods`에 `@Version`이 없어 진짜 낙관적 락 충돌이 아니다. DELETE 영향 행이 0건일 때 Hibernate가 던지는 `StaleStateException`을 Spring이 번역한 것이다. 같은 회원·상품으로 POST가 거의 동시에 두 번 들어와 둘 다 같은 행을 삭제하려다 나중 트랜잭션이 실패한다. 벌크 삭제 쿼리나 upsert로 바꾸면 된다.

- **[11:30] Q.** 두 번 호출되는 것부터가 문제인데, price랑 recent-goods가 두 번씩 되네? 운영은 괜찮은데 dnm-web 봐줄래?
  **A.** dnm-web 코드는 dev와 production이 같고 차이는 실행 모드다. `reactStrictMode: true`라 `next dev`에서만 effect가 두 번 돌아 상세 페이지의 status → price → base → recent-goods 4개 API가 모두 두 번 나간다. 이를 막는 `dedupe.ts`는 3월 커밋에서 본문이 주석 처리되어 통과 함수 상태다.

- **[11:36] Q.** in-flight는 뭐고 dedupe은 뭐지?
  **A.** dedupe는 같은 요청이 짧은 시간에 여러 번 와도 한 번만 실행하는 중복 제거다. in-flight는 아직 응답이 안 온 진행 중 요청이다. 같은 key의 진행 중 Promise가 있으면 그것을 공유하는 방식이다. POST는 in-flight만, GET은 TTL 캐시까지 쓰는 게 안전하다.

- **[11:39] Q.** StrictMode는 뭐고 로컬 개발에는 어떻게 수정하는 게 좋아? 왜 저렇게 해놨는지도 추측해줘.
  **A.** React의 개발 중 검사 모드로 effect를 일부러 두 번 실행해 cleanup 누락을 드러낸다. `create-next-app` 기본값이 켜짐이라 그대로 둔 것으로 보이고, `dedupe.ts`는 3월 디버깅 중 끄고 복원을 잊은 모양새다. StrictMode는 두고 `dedupe.ts` 복원과 API 벌크 DELETE 전환을 권장한다.

- **[11:42] Q.** API 쪽 `addRecentGoods`만 벌크 DELETE로 바꾸고 dnm-web은 그냥 둬도 되는 거지?
  **A.** 된다. 벌크 DELETE는 영향 행 0건이어도 예외가 없어 두 요청 모두 정상 응답한다. `addRecentGoods`와 `limitRecentGoodsCount` 두 곳을 수정했고 오프라인 컴파일을 통과했다. 완전 동시 요청이면 행 2건이 잠깐 남을 수 있지만 조회가 goodsNo로 중복 제거해 화면 영향은 없다.

- **[11:46] Q.** `SessionContextHolder.getFoUser()` 세션에 없을 때는 오류 나지 않나? 삭제니까 방어 로직 포함해줄래?
  **A.** 맞다. 세션이 없으면 `getFoUser()`가 null이라 NPE가 났다. null이면 INVALID_TOKEN `ValidationException`, 거래처·회원·상품 키 중 하나라도 비면 파라미터 누락 `ValidationException`을 던지도록 했다. 검증된 값을 삭제·등록·개수 제한에 재사용한다.

- **[15:23] Q.** 테스트 코드도 만들어줄 수 있어? owgerp22 계정에 최근본상품 50개 넘게 있거든.

- **[15:56] Q.** 여기에 해놓으니까 테스트 코드를 실행할 수가 없는데?
  **A.** shell 프로젝트에 `src/test` 폴더가 처음 생겨 IntelliJ가 테스트 소스로 인식하지 못했을 가능성이 크다. Maven 프로젝트 새로고침을 하거나 Test Sources Root로 지정하면 된다. member 수정분은 shell이 jar로 참조하므로 먼저 install 되어 있어야 한다.

## 이슈와 배운 점
- `@Version` 없는 엔티티에서도 `ObjectOptimisticLockingFailureException`이 난다. DELETE 영향 행 0건 시 `StaleStateException`이 번역된 것이다.
- 엔티티 `deleteAll`은 동시 요청에 취약하다. JPQL 벌크 DELETE는 영향 행 0건이어도 예외가 없다.
- React StrictMode는 dev에서만 effect를 두 번 실행한다. 운영에서 안 보인다고 문제가 없는 게 아니라 더블클릭·탭 두 개로 재현될 수 있다.
- `dedupe.ts` 같은 방어 유틸이 "test" 커밋에서 주석 처리된 채 운영까지 올라갔다. 주석 처리 임시 조치는 복원 여부를 반드시 확인해야 한다.
- 세션 값을 삭제 조건으로 쓸 때는 null 방어가 필요하다. JPQL에 null이 들어가면 전체 삭제로 번지진 않지만 어정쩡한 상태가 된다.
- member 모듈은 8월 26일 라이브러리화 이후 `@SpringBootTest`가 부팅되지 않는다. 기존 `MileageServiceIntegrationTest`도 같은 이유로 실행이 안 된다.
- shell 프로젝트 테스트 실행 시 member 수정 후 `install`이 먼저 필요하다. `-Dtest`에 와일드카드가 없으면 Nested 안쪽만 돌고 바깥 동시성 테스트가 빠진다.
