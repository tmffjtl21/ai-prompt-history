## 질문과 답변 기록

- **[22:56] Q.** 위키에서 오스템몰 쪽은 너무 간단히 썼는데 수정해야 될 내용 있을까?
  **A.** 있다. 1번은 제목이 관계 관리인데 내용은 토큰 얘기만 있고 토큰 발급 주체·클레임이 없다. 2번은 동기화 방향이 없고 탈퇴·정지·이메일 변경 이벤트가 빠졌다. 3번은 방향이 반대로 읽히고 용도·증분 조건이 없다. 구조적으로 거래처 원장 이원화(ERP vs 통합회원)와 로그인 설계 변경(OIDC 복귀 여부)을 먼저 정해야 한다. 붙여넣기용 수정안과 추가 제안 항목(로그인 연동, 회원가입, 마이그레이션, 보안·장애 대응)을 제시했다.

- **[23:10] Q.** OIDC가 뭐야?
  **A.** OpenID Connect. OAuth 2.0 위에 로그인(인증)을 얹은 표준 프로토콜로 구글·카카오 로그인 방식이다. 몰이 통합회원 로그인 화면으로 리다이렉트하고 일회용 코드를 ID 토큰(JWT)으로 교환해 비밀번호를 다루지 않고 사용자를 식별한다. 국내 오스템몰의 `sso-login` 리다이렉트 + RS256 JWT 수신이 사실상 이 방식이고, 몰 shell은 이미 JWKS 검증 구조라 발급기만 바꾸면 된다.

- **[23:15] Q.** 동기화가 많은데 몰 API는 기존 `memberSyncMgmt` 명세 기준 이거만 적으면 돼?
  **A.** 한 줄로는 부족하다. 몰 수신 API 8개 중 해외에서 그대로 쓸 수 없는 것과 없는 이벤트가 섞여 있어 이벤트별 표로 적어야 한다. 거래처 수정 API는 ERP가 원본이면 삭제 대상이고, 탈퇴·정지·복구, 이메일(로그인ID) 변경, 마케팅 수신 동의 변경은 현재 API로 처리할 수 없다. 재시도 안전, U/D 플래그, 응답 코드 같은 공통 규칙도 명시해야 한다.

- **[23:20] Q.** 회원 탈퇴·정지·복구 API가 어디지? 새로 만들어야 하나?
  **A.** 탈퇴는 있고 정지·복구는 없다. 탈퇴는 api-member `WithdrawalController`의 `/withdrawal/check`와 `/withdrawal`이며 permit-all로 열려 있어 서버 간 인증과 세션 무효화 추가가 필요하다. 정지·복구는 `mergeMemberSync`가 상태 컬럼을 건드리지 않아 신규가 필요하며, 상태 변경 API 하나로 묶는 것을 제안했다.

- **[23:21] Q.** 정지는 회원정보 수정에서 받으면 되고, 탈퇴는 저기 보라고 하면 되네
  **A.** 그렇게 가면 된다. 요청 DTO에 `mbrStatCd`가 이미 있으니 매퍼에 `MBR_STAT_CD` 갱신을 추가하고 정지 시 세션 삭제를 함께 호출한다. 탈퇴는 check를 먼저 호출해 불가 사유가 있으면 중단하는 순서만 명시하면 된다.

- **[23:25] Q.** 표 지금 정리했는데 다시 봐줄래?

## 이슈와 배운 점
- 요구사항 문서에서 화살표(→)를 데이터 방향과 호출 방향으로 섞어 쓰면 제공 주체가 반대로 읽힌다. 화살표 대신 주체를 글로 명시하는 편이 안전하다.
- 거래처 마스터 원본을 ERP로 정했는데 통합회원 동기화 API에 거래처 등록·수정이 남아 있으면 ERP 배치 값과 서로 덮어쓴다. 원본 시스템 결정과 API 목록을 함께 맞춰야 한다.
- `mergeMemberSync`는 회원명·이메일·휴대폰만 갱신하고 상태 컬럼은 갱신하지 않는다. 상태 변경을 이 이벤트로 받으려면 매퍼 수정이 필요하다.
- 탈퇴 API는 permit-all로 열려 있고 세션 무효화를 하지 않는다. 서버 간 인증과 `revoke` 연결이 보안 항목에서 다뤄져야 한다.
- `r_cst_email`은 거래처 단위 이메일이며 값이 있는 거래처가 약 27%에 그친다. 회원 로그인ID로 쓸 수 있는지 확인 필요.
