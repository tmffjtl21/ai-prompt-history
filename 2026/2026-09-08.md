## 이슈와 배운 점
- **커밋 시점 락 예외의 실체**: InnoDB 락 오류는 COMMIT 이 아니라 SQL 문 실행 응답으로 온다. JPA 는 write-behind 라 커밋 직전 flush 에서 SQL 이 나가면 예외 위치가 프록시가 되어 메서드 안 catch 가 못 잡는다.
- **자동 flush 에 우연히 의존**: 긴급배송의 주문 INSERT 는 `findByOrdNo` JPQL 조회가 유발한 자동 flush 로 메서드 안에서 실행된다. 조회를 없애거나 위치를 바꾸면 보상 안 되는 구간이 넓어진다. 명시적 flush 로 의도를 드러내야 한다.
- **rollback-only 와 삼켜진 예외**: 참여 트랜잭션의 `@Transactional` 메서드가 예외를 내고 상위가 삼키면 커밋에서 `UnexpectedRollbackException` 이 나고 catch 보상이 실행되지 않는다. 배치 락과는 별개 문제다.
- **배치의 공유 락**: REPEATABLE READ 에서 `INSERT ... SELECT` 는 원본 행에 공유 next-key 락을 잡는다. dev 는 `SM_DAYCL_ORD_AGRT` 의 max(AGRT_DT) 가 4월이라 기준일이 5개월 전이고 실행계획도 풀스캔이라 락 범위와 시간이 모두 크다. READ COMMITTED 로 내리면 락 없는 일관 읽기가 된다.
- **AFTER_ROLLBACK 리스너의 한계**: 커밋은 됐는데 응답만 유실된 경우 rollback 이 no-op 성공하면 정상 주문의 PG·SAP 를 취소할 수 있다. R23 이 UNKNOWN 판정을 따로 둔 이유다.
- **테스트 주의**: 프로브 테스트는 dev DB 의 계약 4550 실데이터에 의존한다. 스케줄이 발송 처리되면 상수를 바꿔야 한다. pom 의 skipTests 를 임시로 false 로 바꿔 실행한다.
